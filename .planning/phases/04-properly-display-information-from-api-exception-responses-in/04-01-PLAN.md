<objective>
Create the ChronoscopeError model with errorCode mapping and enhance the error interceptor to parse the full ProblemDetail structure from backend responses.

Purpose: The backend returns rich error metadata (errorCode, type URI, fieldErrors) inside ProblemDetail's `properties` map that the current interceptor ignores. This plan parses that metadata, maps errorCodes to user-friendly titles, and re-throws a typed ChronoscopeError so callers can handle errors programmatically.

Output: ChronoscopeError model, errorCode-to-title mapping, enhanced interceptor, extended Notification model.
</objective>

    1. A `FieldError` interface with two required string properties: `field` and `message`.

    2. An `ApiErrorCode` string literal union type containing exactly these values: `API_NOT_IMPLEMENTED`, `INSUFFICIENT_SLOTS`, `RESOURCE_NOT_FOUND`, `VALIDATION_ERROR`, `INVALID_REQUEST`, `ACCESS_DENIED`, `ACCOUNT_NOT_FOUND`, `INTERNAL_SERVER_ERROR`.

    3. A `ERROR_CODE_TITLES` constant — a `Record<ApiErrorCode, string>` mapping each code to its backend-synced title:
       - `API_NOT_IMPLEMENTED` → `'Not Implemented'`
       - `INSUFFICIENT_SLOTS` → `'Planning Failed'`
       - `RESOURCE_NOT_FOUND` → `'Not Found'`
       - `VALIDATION_ERROR` → `'Validation Failed'`
       - `INVALID_REQUEST` → `'Invalid Request'`
       - `ACCESS_DENIED` → `'Access Denied'`
       - `ACCOUNT_NOT_FOUND` → `'Account Not Found'`
       - `INTERNAL_SERVER_ERROR` → `'Internal Server Error'`

    4. A `ChronoscopeError` class that extends `Error` with:
       - Constructor takes `HttpErrorResponse` and optional parsed ProblemDetail body (the already-extracted JSON body, not the raw response).
       - Readonly properties: `errorCode` (ApiErrorCode or undefined), `typeUri` (string or undefined), `fieldErrors` (FieldError[] or undefined), `detail` (string or undefined), `title` (string — resolved from errorCode map with fallback to ProblemDetail title, then status-based fallback), `status` (number), `httpError` (the original HttpErrorResponse).
       - Parsing logic: if body is a ProblemDetail (has `detail` or `title`), read `properties?.['errorCode']` as errorCode, `type` as typeUri, `properties?.['fieldErrors']` as fieldErrors. Use `ERROR_CODE_TITLES[errorCode]` for title when errorCode is present; fall back to `body.title`; fall back to status-based title using the same logic as the existing `statusTitle` function.
       - Set `this.name = 'ChronoscopeError'` and `this.message` to `detail` or a fallback message.

    5. Export a standalone `parseErrorBody` function that takes `(body: unknown, error: HttpErrorResponse)` and returns a `ChronoscopeError` — this centralizes the parsing logic for both JSON and Blob-then-JSON paths.

    Then edit `src/app/model/notification.model.ts`:
    - Add an optional `fieldErrors` property to the `Notification` interface typed as `Array<{ field: string; message: string }>`. Import nothing — use an inline type to avoid circular dependency with the error model.
